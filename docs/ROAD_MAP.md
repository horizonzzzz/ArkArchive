## 一、 背景与现状调研

### 1. 现有工具分析（以 Arkstage 为例）
* **现状**：社区曾有开源项目 `djkcyl/arkstage`（Tauri v2 + React），将 PRTS Wiki 的网页演出引擎内嵌在 WebView 中运行。
* **致命痛点**：该工具过度依赖向 PRTS Wiki 实时请求其网页运行时私有接口（如 `StoryPlayer context/manifest`）。近期 PRTS Wiki 进行了站内小部件体系重构（向现代化微件迁移），导致其私有接口格式发生变更，Arkstage 出现 `StoryPlayer context/manifest 接口发生变化` 崩溃，且因长期未维护彻底失效。
* **核心教训**：**不能通过抓取 PRTS 私有接口或内嵌其脆弱的外部运行时来开发**。必须直接基于底层原始解包数据，建立一套独立自主、结构解耦的播放引擎。

## 二、 数据源与多媒体资源规划

所有的资源获取必须绕过第三方的动态私有 API，统一采用公开、稳定且随游戏发包自动更新的数据源。

### 1. 剧情文本与结构大纲（GitHub 解包仓库）
* **数据源仓库**：`Kengxxiao/ArknightsGameData`（全服同步，由自动化工作流随游戏发包持续维护）。
* **核心依赖文件**：
  * **剧情索引大纲**：`zh_CN/gamedata/excel/story_review_table.json`
    * 映射了所有主线、插曲、别传、故事集、干员密录的先后关系、关卡名与剧情脚本路径。
  * **原始剧情脚本**：`zh_CN/gamedata/story/**/*.txt`
    * 鹰角原生的 DSL 文本，文件体积仅数 KB，包含所有台词、立绘变换、音效指令。

### 2. 媒体素材（立绘、背景、BGM、音效）
* **体积问题**：全量明日方舟多媒体素材高达数十 GB，严禁随安装包分发。
* **获取策略**：由本地解析器扫描当前剧情脚本，生成该关专属的资源依赖清单，按需下载。
* **公开静态源（CDN）**：
  * **背景图**：`https://static.prts.wiki/assets/bg/{image_name}.png`
  * **立绘图**：`https://static.prts.wiki/assets/character/{char_id}.png`
  * **音频/音乐**：`https://static.prts.wiki/assets/audio/{music_key}.mp3`
  * *注：PRTS 静态资源路径稳定公开，直接通过规则拼接下载，不触发动态接口限制。*

## 三、 PRTS 剧情播放器原理解析与参考复用

PRTS 的核心演出引擎（`ScenarioSimulator` / `StoryPlayer`）运行于浏览器端，本质是一套基于事件队列的 AVG 视觉小说脚本状态机。

### 1. 官方脚本语法格式（DSL）
剧情脚本主要分为两类行：
* **指令行**：以 `[` 开头、`]` 结尾，例如：
  * `[Background(image="bg_corridor", screenadapt="coverall")]`
  * `[Character(name="char_003_kalts_1", focus=1)]`
  * `[PlayMusic(intro="$tech_intro", key="$tech_loop", volume=0.8, crossfade=1.5)]`
  * `[Blocker(a=1, r=0, g=0, b=0, fadetime=2, block=true)]`
  * `[Decision(options="选项A;选项B", values="1;2")]`
  * `[CameraShake(duration=1, xstrength=5, vibrato=20)]`
* **台词行**：直接为对话，或带有说话人属性：
  * `[name="凯尔希", color="#008000"] 这次又要做什么？`

### 2. 从 PRTS 源码中重点参考的业务黑盒
在浏览器打开任意 PRTS 剧情页，F12 在 Sources 中美化 `ScenarioSimulator.js` 即可直接阅读，重点参考：
1. **阻塞与并发机制**：`block=true` 代表阻塞播放队列，必须等待动画/音频过渡结束才允许继续；`block=false` 为非阻塞并发执行。
2. **多角色焦点计算**：双人/三人站位时，未发言角色通过透明度与对比度矩阵暗淡化（`brightness(0.6)` / `opacity: 0.7`）。
3. **BGM 无缝循环（Intro + Loop）**：前奏播放完毕后无缝切换主节循环的音频调度逻辑。
4. **分支与条件跳转**：`[Decision]` 捕获玩家选择，后续由 `[Predicate]` 执行逻辑分支过滤。

## 四、 移动端技术栈选型对比

| 框架 / 方案 | 演出还原度 | 动画/音效控制力 | 开发成本 | 离线缓存适配 | 综合推荐指数 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Flutter** | **极高**（自绘引擎） | **极强**（毫秒级同步） | 中 | 极佳 | **★★★★★（首选）** |
| **Capacitor + Web Canvas** | **极高**（Pixi.js/DOM） | 优秀（Web Audio API） | 最低（纯前端体系） | 良好 | **★★★★☆（备选）** |
| **React Native (Bare)** | 良好（原生 View） | 较好（Reanimated） | 较高（跨桥调用） | 良好 | ★★★☆☆ |
| **Expo (RN)** | 一般 | 受限（音频低延迟难控） | 低 | 受沙盒限制 | ★★☆☆☆ |

### 为什么首选 Flutter？
1. **视觉小说本质就是 2D 游戏**：Flutter 底层基于 Impeller/Skia 自绘，图层叠加（Stack）、透明度渐变（AnimatedOpacity）、矩阵变换（Transform 震屏/缩放）性能极高，不会出现 React Native 原生跨桥通信的动画掉帧或图层重绘卡顿。
2. **原生沉浸式控制**：进入播放器时一键强制全屏锁定横屏（`landscape`）并隐藏状态栏，退出时平滑恢复。
3. **音频无缝处理**：借助 Flutter 社区极其成熟的 `just_audio`，原生支持低延迟音效触发与 BGM 前奏/主节无缝循环。

## 五、 自研播放器核心架构设计

为了保证未来游戏更新新增演出方式时 App 不会崩溃，必须采用**注册制指令分发器架构（Command Dispatcher Pattern）**。

```text
              +----------------------------------+
              |    原始剧情脚本 (.txt / DSL)     |
              +----------------------------------+
                               |
                               v
              +----------------------------------+
              |     词法解析器 (Script Parser)   |
              |   - 正则逐行扫描                  |
              |   - 输出 AST 指令流队列          |
              +----------------------------------+
                               |
                               v
+----------------------------------------------------------------+
|                 播放器运行时 (Story Player Engine)             |
|                                                                |
|  [ 指令分发中心 (Command Dispatcher) ]                          |
|    - 查找 Handler 字典                                         |
|    - 遇到未知 Tag -> 走 UnknownHandler 打印 Warning 并跳过     |
|    - 绝不阻断崩溃，保证向下平稳兼容                            |
|                                                                |
|  [ 状态机模型 (Stage State Machine) ]                          |
|    - 当前背景图 / 滤镜状态                                     |
|    - 角色立绘插槽 (Left / Center / Right / Focus)              |
|    - 全屏遮罩层 (Blocker Alpha / Color)                        |
|    - 对话框与打字机输出状态 (Typewriter / Log)                 |
|    - 音频控制器 (BGM Loop / Sound Effects)                     |
+----------------------------------------------------------------+
                               |
                               v
              +----------------------------------+
              |        渲染展示层 (Flutter UI)   |
              |   - Stack 分层自绘渲染           |
              |   - 手势点击驱动推进             |
              +----------------------------------+
```

### 1. 优雅降级设计（防崩溃关键）
* 每个指令对应一个独立的处理器类（如 `CharacterHandler`、`BackgroundHandler`）。
* **兜底保护**：当游戏出了全新的未知指令（如 `[NewEffect_2026]`），调度器自动交由 `UnknownCommandHandler` 忽略并推进到下一指令，**App 永不闪退，剧情对话继续推进**。
* **平滑跟进更新**：当 PRTS 适配了新演出后，开发者只需在本地新增一个 Handler 类注册进字典，即可零侵入完成升级。

## 六、 离线缓存与多媒体资源管理

1. **内容寻址去重存储**：
   * 明日方舟跨章节复用大量立绘与 BGM。本地使用文件真实名称/Hash 作为存储文件名（例如 `storage/characters/char_003_kalts_1.png`）。
   * 无论下载多少个章节，同一素材在手机存储中仅占一份空间。
2. **下载策略**：
   * **按需预下载**：进入某关卡前，解析该关 txt 提取全部图片与音频，一键批量下载。
   * **在线边看边存**：若在线浏览未下载章节，网络拉取到的素材自动写入本地闪存，二次打开完全离线。
3. **存储空间压缩（可选高级优化）**：
   * 手机端可集成简单的图片转码器，将已缓存的 PNG 图片在本地无损或高质量压缩为 WebP 格式，可削减 50%~80% 的磁盘空间。

## 七、 分步实施与落地路线图

* **阶段 1：数据层与目录展示（约 0.5 天）**
  * 抓取 `Kengxxiao/ArknightsGameData` 中的 `story_review_table.json`。
  * 搭建基础 Flutter App，展示主线、活动与干员密录树状列表。
* **阶段 2：解析器与下载器开发（约 1 天）**
  * 编写纯 Dart 的正则 Lexer，把 `.txt` 转换成结构化 `List<StoryCommand>`。
  * 提取素材清单，对接 PRTS 静态 CDN 实现多线程并发下载与本地文件系统持久化。
* **阶段 3：播放器核心渲染骨架（约 1~2 天）**
  * 强制横屏沉浸式页面。
  * 搭建 4 层基础视觉：背景层、立绘层（支持左右中槽位与焦点透明度切换）、全屏黑幕转场、底部文字对话框。
  * 实现点击屏幕步进、打字机逐字输出文字效果。
* **阶段 4：音频与分支系统补全（约 1 天）**
  * 接入 `just_audio`，实现 BGM（带 crossfade 与 loop）和 SE 音效触发。
  * 实现 `[Decision]` 选项弹窗与选择支跳转逻辑。
* **阶段 5：演出打磨与异常防护（持续迭代）**
  * 参考 PRTS 源码校准震屏幅度（Matrix 动画）和立绘位移动画。
  * 注入 `UnknownCommandHandler` 防御性代码，发布首个完全离线运行的 Android APK。
