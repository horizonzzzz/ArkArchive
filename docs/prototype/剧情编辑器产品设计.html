PRODUCT DESIGN / v0.1

剧情编辑器 · 产品分析设计

面向「方舟档案室」的本地创作工具：用 PRTS 素材与本地素材，编排一段可直接播放的剧情演出。本文覆盖产品定位、能力边界、核心模型、双端界面、效果映射、素材与导出方案、分期与验收，不包含代码实现。

项目：arknights_story_player 形态：桌面横屏 / 移动端竖屏 画布：1280 × 720 更新：2026-11-12

结论先行：编辑器不应做成「时间轴剪辑器」，也不应做成「脚本文本框」。推荐以 分镜（Beat） 为最小创作单位、以 舞台状态 为真相、以 脚本 为编译产物：一套数据模型，三种视图（故事板、舞台、时间轴），两端各自组织界面而不是缩放同一套界面。

一、产品定位与目标

「剧情编辑器」是播放器的反向工具：播放器把脚本解释成演出，编辑器把创作者的意图编译成脚本。它服务于「我想用方舟的素材，做一段自己的剧情演出」，而不是「我想修改游戏原版剧情」。

产品定位

本地优先的演出创作台：素材可来自 PRTS，也可来自本机；作品只存在本地，可导出为可移植的剧本包。

不做账号 不做云同步

核心价值

把「写指令」变成「摆画面」：先看到结果，再微调参数；常用演出有预设，复杂演出仍可下探到参数与命令。

成功标准

新用户 5 分钟内能完成「背景 + 两个立绘 + 三句对白」并播放；熟练用户能在不手写脚本的情况下完成带运镜、遮罩、分支的短片。

目标

  • 覆盖引擎已支持的主流演出：对白、背景、立绘、文字、音频、运镜、遮罩、镜头特效、选项分支。
  • 桌面端可高效批量编排；移动端可随时查看、改台词、调位置、做轻量演出。
  • 作品可保存、可恢复、可导出、可再导入；导出物在播放器内行为确定。
  • 不引入「编辑器能配、播放器演不出」的假能力。

非目标（本期明确不做）

  • 不做视频剪辑、特效合成、逐帧动画；引擎不支持的 video、effect、bgeffect、spellsticker 不提供开关。
  • 不做在线作品广场、账号体系、云端协作、跨设备同步。
  • 不修改原版 PRTS 脚本；对原版剧情只提供「派生为新作品」的导入。
  • v1 不产出竖屏成片，竖屏只是编辑与预览的界面形态（见第十六节待拍板项）。

关键约束：播放器舞台固定为 1280×720 逻辑坐标，文字、立绘、遮罩的所有位置参数都基于该坐标系。竖屏手机上的画布是被缩放的 16:9 视口，不是另一套 720×1280 舞台；这决定了「移动端竖屏编辑」只能是布局适配，不能改变成片比例。

二、现状能力盘点

编辑器的能力上限由播放器解释器决定。现状是「命令覆盖较全、但部分命令语义不完整」，因此产品必须先做能力分层，再决定暴露方式。

产品原则：不做假控件。凡是不能稳定播放的能力，不放进常规面板、不进入预设、不生成教程。用户看不到的按钮，比点了没反应的按钮更可信。

三、用户与核心场景

同人创作者

熟悉角色与素材，想快速把脑内桥段做出来。关心素材好不好找、演出像不像原作、能不能导出分享。

  • 高频：找立绘差分、摆三人构图、加 BGM
  • 低频：分支、复杂遮罩

剧情区内容作者

需要批量产出短剧情用于配音或视频二创，关注效率与一致性，愿意学习高级参数。

  • 高频：连续对白、重复模板、批量改台词
  • 依赖：导出脚本、时间轴精修

轻度玩家

在手机上随手改几句台词、看看效果，不追求复杂演出。关心能不能单手完成、会不会误操作。

  • 高频：改台词、换表情、调文字位置
  • 依赖：大按钮、撤销、自动保存

典型任务流

  1. 5 分钟 Quick Start
    新建作品 → 选背景 → 放入两个立绘 → 写三句对白 → 播放。全程不接触命令与坐标。
  2. 30 分钟 精修一段演出
    在舞台上直接拖动立绘与文字 → 加「缓慢推近」运镜 → 调时长与缓动 → 加黑屏转场 → 从当前分镜循环预览。
  3. 跨设备 连续创作
    桌面端完成主体编排 → 导出剧本包 → 手机端导入继续改台词与位置；不做云同步，靠文件传递。
  4. 复用原版剧情
    从剧情馆选择一篇已缓存剧情「派生为我的作品」，保留原指令序列，仅替换对白与素材，不修改原脚本。

四、编辑模型的三个方案

在进入界面之前，必须先确定「用户编辑的到底是什么」。这决定了双端布局、预览方式与导出格式。

A. 纯时间轴

像剪辑软件：轨道 + 关键帧
  • 优点：动画时序直观，适合并行演出
  • 缺点：对白这种离散内容不适合放轨道；状态累积（谁还在台上、BGM 是什么）不可见；移动端极难操作
  • 结论：不作为主视图，只作为局部精修工具

B. 分镜 + 舞台（推荐）

像故事板：一屏一个意图，舞台即结果
  • 优点：符合「一句台词 / 一个动作」的创作直觉；状态可见；双端都能操作
  • 缺点：并行动画需要在分镜内用微时间轴表达
  • 结论：作为主模型，时间轴降级为分镜内的时序条

C. 纯脚本编辑器

像代码编辑器：直接写命令
  • 优点：实现成本最低，能力最全
  • 缺点：只服务少数人；无法做到「所见即所得」；与产品定位冲突
  • 结论：作为高级模式与导入兼容层保留

推荐 B 的核心理由：引擎的脚本是命令式的、状态累积的，而剪辑式时间轴假设「每个轨道独立且可随机访问」。分镜模型把「意图」作为单位，编译时才展开成命令与并行动画，既贴合引擎，也贴合用户的心智。

五、核心产品模型

5.1 四层结构

作品 Project标题、封面、素材库、设置、版本
→
幕 Scene连续舞台状态；换场时重置或保留
→
分镜 Beat一个创作意图：一句台词、一次出场、一段运镜
→
指令 Command编译产物；一个分镜可生成 1~N 条命令

分镜是唯一的编辑单位。它有三个关键字段：类型（对白 / 立绘 / 背景 / 文字 / 音频 / 特效 / 选项 / 等待 / 高级）、参数（面向用户的语义字段）、时长与阻塞（是否等待动画结束再继续）。

5.2 状态是真相，脚本是结果

剧情演出不是「一张张独立画面」，而是状态不断累积：背景还在、立绘还在、BGM 还在、遮罩还盖着。编辑器必须让这些状态可见，否则用户从中间预览时会出现「立绘凭空消失」「BGM 突然开始」的困惑。

  • 舞台状态快照：每个分镜执行后记录背景、各槽位立绘、文字、遮罩、镜头、音轨的状态；编辑时在舞台下方以「当前状态」标签呈现。
  • 确定性重演：从某个分镜预览时，从所属幕的开头重演到该分镜；重演不播放音效、不触发等待、不写观看进度，最多执行固定步数防止死循环。
  • 编辑不依赖回放：快照仅用于预览与拾取；作品文件仍以分镜参数为真相，避免把运行时状态写进作品导致漂移。

七、双端界面设计

桌面与移动不是同一界面的缩放。桌面是「编排台」，强调信息密度、并行操作与批量编辑；移动是「随身修改器」，强调画布可见、单手可达、随时收起。两端共享舞台渲染、检查器字段定义与分镜数据，不共享布局。

竖屏采用「舞台常驻 + 卡片式当前分镜 + 横滑分镜轨」结构。属性从底部抽屉进入，按「基础 / 演出 / 音频 / 高级」分段；键盘弹出时舞台缩为窄条或折叠，保证输入框与候选词可见。复杂动画参数在移动端只给预设与时长，数值微调让位给桌面端。

7.4 移动端横屏与平板

  • 横屏手机：左侧 58% 舞台，右侧分镜列表；工具条浮在舞台底部；属性为右侧全高抽屉。适合看效果与快速切换，不适合长文本录入。
  • 平板横屏：接近桌面双栏，保留底部时间轴，但把左栏收起为图标栏，避免压缩舞台。
  • 统一规则：无论何种布局，舞台始终按 16:9 等比缩放，编辑坐标以 1280×720 换算，不使用屏幕像素直接存储。

竖屏的两个易错点：① 舞台高度只有约 56vw，拖动立绘时手指会遮挡目标，需提供「选中后出现偏移控制条 / 微调步进」；② 竖屏下若直接显示完整时间轴，会挤占舞台与输入区，因此移动端只保留「时长 + 缓动预设」，不做多轨编辑。

八、编辑交互

8.1 舞台直编

  • 选择：点选最上层可见对象；再次点击穿透到下一层；左栏分镜点击可定位到对应对象。选中态显示包围框、对象名与快捷操作。
  • 拖动：立绘拖动写入槽位偏移（position），文字拖动写入 x/y，背景拖动写入图层位移。拖动时实时显示逻辑坐标，松手后吸附。
  • 吸附：立绘吸附三槽位中心、画面中线、底部基线；文字吸附左右安全边距与水平中线；按住修饰键或关闭吸附可自由摆放。
  • 缩放与旋转：桌面用包围框手柄，移动用双指；立绘缩放写入 zoom 参数并保持锚点；旋转写入 angle，背景旋转是整幅画面旋转，需在属性中明确提示作用范围。
  • 拖入素材：从素材库拖到舞台，按落点自动判断类型：拖到背景区域建背景，拖到立绘区域建立绘，拖到文字区域建文字；落点不确定时弹出类型选择。
  • 安全区：默认显示字幕安全区与底部对白框占位，避免把关键内容放到会被对白遮挡的位置。

8.2 分镜卡片与插入

分镜列表是编辑器的主干。每张卡片包含：类型图标、缩略图或对象摘要、说话人 / 素材名、首行文本、演出标签、时长与阻塞标记。卡片支持拖拽排序、多选、复制、禁用（临时跳过）、折叠。

8.3 检查器

检查器不是「所有参数的列表」，而是「当前对象最可能的下一步」。字段按对象类型动态生成，常用项在前，高级项折叠；每个数值字段同时提供滑杆、步进与直接输入，并显示单位与取值范围。

  • 基础：槽位、素材、差分、位置、透明度、时长。
  • 演出：动作类型、起点与终点、缩放、旋转、缓动、循环、是否阻塞。
  • 音频：BGM / 音效、音量、淡入淡出、是否循环。
  • 高级：只读展示将生成的命令与参数；可切换为「直接编辑命令」但不建议普通用户使用。

8.4 分镜内时间轴

  • 只展示当前分镜编译出的并行轨道：立绘淡入、背景推近、文字出现、音频淡入等。轨道不是独立编辑对象，而是参数的可视化。
  • 拖动轨道块改时长与延迟；拖动缓动点改曲线预设；不支持任意关键帧，避免把简单模型做成半成品剪辑器。
  • 时间轴上的播放头可拖动，舞台实时呈现该时刻的中间帧；松手回到分镜起点或停在当前位置。
  • 移动端折叠为「时长 / 延迟 / 缓动」三个字段，必要时提供单行迷你时间轴。

8.5 连续对白与批量操作

  • 连续对白模式：在台词卡片中按回车即新建下一句，自动继承说话人；空行退出；支持从剪贴板按「说话人：台词」批量粘贴。
  • 批量替换：按作品范围替换说话人或素材，先预览影响的分镜数量再执行。
  • 模板：把常用组合存为「演出模板」（背景淡入 + 双人入场 + 推近），插入后只替换素材与台词。
  • 撤销：至少 50 步；舞台拖动合并为一次操作；撤销跨分镜有效。移动端提供常驻撤销按钮与轻提示。

十、素材中心

10.1 双来源

PRTS 素材

沿用播放器现有的资源映射规则：立绘来自 character.json，背景来自 background.json，音频来自剧情变量表。编辑器只做选择器与预览，不复制一套地址规则。

  • 立绘按角色名、别名、差分筛选；网格展示缩略图
  • 背景 / CG 按目录分组，支持关键词搜索
  • BGM / 音效支持试听与最近使用

本地素材

用户上传的图片与音频复制进作品包，引用而非移动原文件；删除作品不影响用户原文件。

  • 图片：PNG / JPG / WebP，建议单张 ≤ 8MB
  • 音频：MP3 / OGG / WAV，建议单个 ≤ 20MB
  • 自动记录尺寸、时长、哈希，重复文件去重

10.2 本地立绘的对齐问题

PRTS 立绘自带尺寸与锚点（size / pos），本地上传的图片没有这些元数据。若直接按原图尺寸摆放，会出现人物忽大忽小、脚底悬空。产品必须在导入时解决：

  • 自动读取像素尺寸，按「底部中心」作为默认锚点，按画面高度归一化到参考身高。
  • 首次放入舞台时进入对齐模式：显示底部基线、三槽位中心与参考身高框；用户可拖动缩放，确认后写入素材元数据。
  • 素材级元数据：锚点、参考身高、可选的脸部区域（供未来差分使用），保存在项目内，跨分镜复用。
  • 不伪造差分：本地图片没有表情组，选择器只显示单张；需要多表情时由用户建立「素材组」，手动标注。

11.3 编译示例

分镜在导出时展开为命令。下面是三个分镜的编译结果，播放器可原生解析：

[background(image="corridor", fadetime=0.3, block=true)]
[charslot(slot="m", name="amiya#1", duration=0.3, focus="m", isblock=true)]
[name="阿米娅"]博士，前面的路已经清理干净了。

编译层需要处理四类细节：参数顺序无关、字符串转义（引号、逗号、反斜杠、换行）、数值格式化（避免科学计数法）、未识别分镜的兜底（降级为高级指令并保留原文）。

十二、预览、校验与保存

12.1 三种预览

  • 单镜循环：只执行当前分镜及其依赖状态，循环播放，用于调节奏与时长。默认不播音效。
  • 从当前播放：从所属幕开头重演到当前分镜，再继续播放，用于检查状态衔接与 BGM。
  • 全片预览：复用正式播放器，隐藏编辑控件，支持暂停、倍速与退出；不写观看进度、不修改断点。

预览必须隔离：编辑器预览与正式观看的进度、断点、缓存作用域要分离。否则用户在编辑器里试看一段，会覆盖正式剧情的「继续观看」，这是不可接受的副作用。

12.2 校验规则

12.3 保存与恢复

  • 编辑即写入本地草稿（防抖 1~2 秒），不依赖手动保存；顶部显示「已保存 / 保存中 / 失败」。
  • 每次打开作品保留最近 20 个自动快照，可回滚；快照只保留 project.json，不复制素材。
  • 崩溃或强制退出后，下次打开提示「恢复未保存的修改」，用户确认后才覆盖当前作品。
  • 素材导入与作品写入分开提交，避免一半素材写入导致作品损坏。

十三、与现有代码的衔接

本节只做可行性判断，不改代码。核心结论：复用绘制与音频，不复用播放控制。播放器为「观看」设计，编辑器需要「随机访问、无副作用、可暂停在中间帧」，两者共用底层状态与画布，但控制层必须分开。

表 10　模块复用与改造点
现有模块复用方式需要的改造
script.dart直接复用解析与转义规则增加反向序列化（命令 → 文本）与参数顺序稳定输出
stage_state.dart / stage_painter.dart直接渲染舞台增加编辑态叠加层：选中框、吸附线、安全区、隐藏交互层
story_engine.dart预览时执行命令增加无等待重演模式、单步执行、按分镜定位；避免副作用写入进度

主要技术风险

  • 状态重建：现有断点恢复依赖「有对白或选项」才算有效停点，编辑器需要停在任意分镜，必须新增无副作用的 seek / replay 路径，并处理动画中间帧。
  • 本地素材解析：MediaCatalog 目前把 PRTS 地址写死，且立绘尺寸来自 character.json；本地素材需要新的解析层与元数据，否则渲染会退回默认尺寸。
  • 音频副作用：重演时若照常执行音频，会重复播放前奏与音效；需要「静默重演 + 恢复音轨」两段式。
  • 绘制性能：舞台叠加层、缩略图、素材网格同时存在时，移动端需限制缩略图分辨率与缓存数量。
  • 命令语义差异：同一个视觉效果可能有多条路径（backgroundtween vs largebgtween、charslot vs character）。编辑器只生成一条规范路径，导入时保留原路径。

十四、分期规划

  1. M0　技术验证
    目标：证明「分镜 → 编译 → 播放器预览」链路可行。范围：单幕、对白 / 背景 / 立绘 / 舞台文字、桌面舞台直编、本地保存。验收：三个分镜的示例作品能导出并在播放器中完整播放。
  2. M1　可用版本
    目标：普通用户可完成一段短片。范围：作品管理、素材选择器（PRTS + 本地）、音频、撤销 / 自动保存、导出与导入、桌面三栏 + 移动竖屏基础布局。验收：新用户 5 分钟完成任务流。
  3. M2　演出增强
    目标：覆盖主流演出。范围：背景运镜、立绘动作、黑色模板、遮罩 / 幕布、镜头震动与灰度、分镜内时间轴、连续对白与模板。验收：不手写脚本完成带运镜与转场的 2 分钟短片。
  4. M3　移动端完善与高级能力
    目标：移动端可独立完成轻量创作。范围：属性抽屉、手势编排、横屏布局、选项分支、原版脚本派生导入、高级指令只读。验收：手机上完成改台词、换表情、调位置、加黑屏并导出。
  5. M4　可选扩展
    目标：提升复用与分享。范围：作品模板、批量替换、素材组、打包 PRTS 素材导出、封面与简介。是否进入取决于前三个阶段的真实使用情况。

排序理由：先打通「能演出来」，再解决「好用」，最后才是「能力全」。把时间轴、分支、CG 图层放到后面，是因为它们成本高、使用频率低，且不影响最小闭环。
